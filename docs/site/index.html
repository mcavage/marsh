Code mode for agents

Compose agents in Bash.

marsh is a Bash-compatible shell for Apple Silicon Macs. Each claude, codex, or pi call runs in its own container in a Docker Sandbox microVM, so you can race agents on private copies of your repo, gate them on your tests, and let an agent hand work to other agents from its own shell.

$ brew install docker/tap/sbx mcavage/tap/marsh

Then sbx login and sbx secret set anthropic (or openai) once. Apple Silicon Macs only. Quickstart →

What you can do

Agents in pipes, scripts, and Makefiles.

marsh adds split and fanout to a Bash-compatible shell. Agents, tests, and linters are all commands, and they compose the same way from an agent's own shell tool.

Race agents on private copies

split runs each branch on its own copy of your working tree, at the same time. join prints each branch's exit status, output, and a patch for git apply. A branch is ordinary Bash, so agent && make test gates each attempt on your tests.

  • Your files change only when you apply a patch.
  • Pipe join into a third agent to choose between passing patches.
  • Up to 16 branches. Ctrl-C stops all of them and everything they started.
Race two agents →   Add a judge → 
marsh-0.5$ split {
>   claude: claude -p "Fix slug.py…" && make test
>   codex:  codex exec "Fix slug.py…" && make test
> } | join --keep
# split 3c8145fd9046: 2 branches; manifest …/out/manifest.json

== claude (exited 0, shell-vm) ==
Fixed `slug.py:6` to collapse runs of non-alphanumerics…
python3 -m unittest -q
-- claude: 1 file (M slug.py); diff …/out/claude/diff.patch --
…
== codex (exited 0, shell-vm) ==
Fixed `slug.py` to collapse separators and trim hyphens…
-- codex: 1 file (M slug.py); diff …/out/codex/diff.patch --

Let an agent farm out work

Inside a marsh job, the same commands are on PATH. An agent can hand a subtask to another agent, run reviewers in parallel, or race fixes and keep the one that passes. Children are processes marsh tracks, not subagents, so any program in a job can start them.

  • Every call lands in one job tree. marsh jobs --tree shows it.
  • Fixed limits: depth 4, 4 live children per job, 64 jobs per tree.
  • MARSH_SPAWN=codex limits what a job may start. Nothing inside a job can widen it.
The guide and AGENTS.md snippet → 
# what the agent runs, from its own Bash tool
$ marsh split -n \
>   ::: codex  codex exec "make test fails. Fix the code…" \
>   ::: claude claude -p "make test fails. Fix the code…" \
>   | marsh join -- sh -c '
    cat
    for b in codex claude; do
      p=$SPLIT_DIR/$b/diff.patch
      test -f "$p" || continue
      grep -qx "exited 0" "$SPLIT_DIR/$b/status" || continue
      if grep -q test "$SPLIT_DIR/$b/files"; then continue; fi
      git apply "$p" || continue
      if make test; then echo "applied $b"; exit 0; fi
      git apply -R "$p" || exit 2
    done
    echo "no patch passed"; exit 1'

Run reviewers and checks side by side

fanout runs branches at once on your real files, with no copies. collect prints each branch's output in the order written and exits with the first failure.

  • Good for tests, linters, and read-only reviews.
  • Branches that write the same file overwrite each other. Use split for writes.
Review with a panel →   Fanout and collect → 
marsh-0.5$ fanout {
>   security: codex exec "Review the uncommitted changes for security bugs…"
>   coverage: claude -p "List behavior in the uncommitted changes that no test covers…"
> } | collect
== security (complete) ==
[P1] `slug.py:12`: `eval(f.read())` allows arbitrary code execution if an
attacker controls the titles file. Use `json.load()` or `ast.literal_eval()`.

== coverage (complete) ==
`load_titles()` has no test at all — nothing covers reading a well-formed
file, and nothing covers its `eval()` of file contents.

Every call in its own sandbox

Each Kit (agent image) gets its own warm Docker Sandbox microVM. A call to claude, codex, pi, or a tool you register runs as a new nonroot container in it, and the container is deleted when the call exits.

  • Your project is mounted at its Mac path. Your Mac home is not mounted.
  • Credentials stay behind the Docker Sandboxes proxy. Containers see placeholders.
  • An agent called directly can still edit or delete project files. Use split to get a patch instead.
  • marsh results records each job's exit status and whether its container was confirmed deleted.

Publish pipelines and agents as MCP tools

mcp publish turns a shell pipeline into an MCP tool that agents in marsh can call. acp publish does the same for a running agent session. Codex on your Mac can load both.

  • marsh mcp install-published codex NAME gives a published pipeline to Codex on the Mac.
  • marsh mcp install lets Claude Code or Codex drive marsh itself.
MCP →   ACP → 
marsh-0.5$ mcp publish flaky -- \
>   'go test -run TestDialTimeout -count=20 ./net/ 2>&1 | tail -3'
marsh-0.5$ mcp load flaky --kit claude
marsh-0.5$ exit
~/src/api $ marsh mcp install-published codex flaky
~/src/api $ codex exec "run flaky and explain any failure"

Keep bash or zsh

marsh --shell zsh or --shell bash runs the VM's own shell with your rc files. You keep agents, MCP, ACP, and the marsh split and marsh fanout CLI forms. You lose the split { } and fanout { } block syntax.

Choosing your shell → 
~/src/api $ marsh config shell zsh   # every launch
% marsh split -n ::: a claude -p "fix it" \
>   ::: b codex exec "fix it" | marsh join
% marsh fanout -n -b test='make test' \
>   -b lint='make lint' | marsh collect

How it works

One daemon, a VM per Kit, a container per call.

  1. Run marsh in your project. A Linux shell opens in a VM at the same path. Edits on either side show up on the other.
  2. Call an agent or tool. The daemon runs it as a new container in that Kit's microVM, with your project mounted.
  3. Agents call agents. A call from inside a job becomes a child job in the same tree, under the same limits.
  4. Look at what ran. marsh jobs --tree and marsh results show each job, how it ended, and whether cleanup finished.
