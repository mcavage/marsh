Bash, extended for agents.

marsh is a Bash-compatible shell with new syntax for parallel agents. Run a few agents on the same bug at once, each on its own copy of your repo, and pipe what they find into another.

$ brew install docker/tap/sbx mcavage/tap/marsh

One branch fixes the test. The other runs two reviewers at once. join hands every branch's output and patch to a third agent, and marsh jobs --tree shows who ran what. Everything else is the shell you know, and every command runs in its own Docker Sandbox microVM.

Why marsh

Agents that compose like commands.

Everything here is a shell command, so it works in scripts, Makefiles, and pipes.

Try several agents on the same bug

split gives each branch a private copy of your working tree and runs the branches in parallel. join collects each branch's output and a patch you can git apply. Your files and your .git don't change until you apply one.

  • Up to 16 branches. An agent branch can only write to its own copy.
  • Pipe the results onward: | join | claude -p "…".
  • fanout { } | collect runs things side by side on the same files, with no copies. Good for tests and lint.
  • Works from plain bash on the Mac, and from inside an agent.
Split and join →   Fanout and collect → 
marsh-0.5$ split { a: claude -p "fix it", b: codex exec "fix it" } | join
# split 8d5c8fdd1563: 2 branches; manifest …/out/manifest.json

== a (exited 0, shell-vm) ==
The test raced on a fixed port; it now asks the kernel for a free one.
-- a: 1 file (M net/dial_test.go); diff …/out/a/diff.patch --
…
== b (exited 0, shell-vm) ==
Added a retry around Dial and a longer timeout.
-- b: 2 files (M net/dial.go, M net/dial_test.go); diff …/out/b/diff.patch --
…

Agents running agents

Inside a job, the registered commands are on PATH. An agent can call another for a second opinion, and every call lands in one job tree.

  • Limits: depth 4, 4 live children per job, 64 jobs per tree.
  • MARSH_SPAWN limits which commands an agent may start. Nothing inside a job can widen it.
  • One Ctrl-C stops the whole tree, and marsh checks that every container is gone.
Agents running agents → 
marsh-0.5$ export MARSH_SPAWN=codex
marsh-0.5$ claude -p "ask codex to review net/dial.go"
marsh-0.5$ marsh jobs --tree
ID        STARTED   STATE      EXIT      RUN  COMMAND
301c56d6  2m ago    finished      0    2m12s  claude -p "ask codex to review net/dial.go"
8e41f0a2  1m ago    finished      0    14.2s  └─ codex exec "review net/dial.go"
marsh-0.5$ claude -p "refactor everything"
^C
marsh-0.5$ echo $?
130

Every command in its own sandbox

Each Kit (the Docker Sandboxes Kit format) gets its own Docker Sandbox microVM. A call to claude, codex, pi, or your own tool runs as a new nonroot container inside it. The container is deleted when the call exits.

  • Your project appears in the Linux VM at its Mac path. Your Mac home is never mounted.
  • Credentials stay behind the Docker Sandboxes proxy. Containers see placeholders.
  • The shell image and packaged Kits are built on Docker Hardened Images.
  • microVMs stay warm between calls. marsh --load all starts them up front.
Commands and Kits → 
~/src/api $ marsh --load claude,codex
marsh-0.5$ pwd
/Users/you/src/api
marsh-0.5$ uname -sm
Linux aarch64
marsh-0.5$ git diff | codex exec 'review this diff' > review.txt
marsh-0.5$ claude -p 'summarize README.md in one line'

Publish pipelines and agents as MCP tools

mcp publish turns a pipeline into an MCP tool that agents can call. A running ACP agent session publishes the same way, so an agent on your Mac can drive an agent in marsh.

  • In marsh: every new Kit VM loads it. mcp load adds it to a running Kit or any sandbox.
  • On the Mac, Codex can load published pipelines and sessions today: marsh mcp install-published and marsh acp install-published.
  • To let Claude Code or Codex drive marsh itself, run marsh mcp install.
MCP →   ACP → 
marsh-0.5$ mcp publish flaky -- \
>   'go test -run TestDialTimeout -count=20 ./net/ 2>&1 | tail -3'
marsh-0.5$ mcp load flaky --kit claude     # new Kit VMs get it; load a running one now
marsh-0.5$ id=$(acp reserve claude-session)
marsh-0.5$ acp run --reservation "$id" claude-session &
marsh-0.5$ acp list --mine --wait "$id" >/dev/null
marsh-0.5$ acp publish "$id" --name net-expert  # a live agent, as a tool
marsh-0.5$ exit
~/src/api $ marsh mcp install-published codex flaky
~/src/api $ marsh acp install-published codex net-expert
~/src/api $ codex exec "run flaky; if it fails, ask net-expert why"
# Codex on your Mac runs a marsh pipeline, then prompts a marsh agent

Use bash or zsh instead

Run the shell VM's own bash or zsh with your own rc files.

  • You keep: registered commands, agents, MCP, ACP, and marsh split, join, fanout, collect.
  • You lose: the split { } and fanout { } block syntax. Use the CLI forms instead.
Choosing your shell → 
~/src/api $ marsh --shell zsh        # this launch
~/src/api $ marsh config shell zsh   # every launch
% marsh split -n ::: a claude -p "fix it" \
>   ::: b codex exec "fix it" | marsh join
% marsh fanout -n -b test='make test' \
>   -b lint='make lint' | marsh collect

How it works

How it fits together

  1. Run marsh in your project. A Linux shell opens in a VM at the same path. Edits on either side show up on the other.
  2. Call an agent or tool. The daemon runs it as a new container in that Kit's microVM, with your project mounted.
  3. Agents call agents. A call from inside a job becomes a child job in the same tree, under the same limits.
  4. Look at what ran. marsh jobs --tree and marsh results show each job, how it ended, and whether cleanup finished.
